# RallyPath 后续独立功能：可执行性优先的战术建议

状态：**候选功能方案，尚未开发或批准发布**。记录于 2026-09-21；不属于已发布 v0.2，也不替代正在推进的「自己画一分 → 找打法／练一项」路径。
后续开发议题：[RallyPath #5](https://github.com/demonyang885/tennis-tactics-interactive-preview/issues/5)。

## 要解决的问题

球员从自己画的一分出发，输入少量画板无法表达的条件，想知道下一拍有哪些适合**自己在当前局面执行**的打法，以及各自的目的和风险。这里的「适合」不是永远唯一的最佳答案；训练时可侧重练习目标，比赛回顾时可侧重当下可执行性和回位。系统必须能回答「信息不足，先和教练讨论」。

本功能作为现有画板和「找个打法」的**可选延伸**，不建立第二套编辑器、独立首页或球场上的实时操作流程。先由孩子画出有意义的一分，再从其中一拍请求比较；不要求每份记录都接受建议，也不覆盖孩子原来的球路或结论。战术候选优先引用现有内容库，必要时展示同一局面的另一种可能，让球员带着一个具体问题去练。

## 本次本地实验给出的边界

独立实验使用 Mac mini M4／16 GB 上的真实本地 `laya-multilingual-coreml`。技术运行成立：模型可离线推理；但冻结的 20 个**合成代理标签**案例中，原始方案仅 2/20 落在预设可接受集合，透明规则为 15/20。后来 v2／v3 在已经暴露的 26 个合成案例上做回顾性探索：v2 最高项只在放短 19 次、深中路 7 次之间切换；v3 为深中路 24 次、放短 2 次，只有 4/26 案例的三种等价表述一致。代理标签未经教练验证；这些结果不能估计真实比赛准确率，却足以否定「把当前 Laya 四选一分数直接当战术建议」这一实现。

Laya 的百分比是给定文字候选的相对分数，不是该球员打成、回合得分或赢球的概率。原模型说明其概率未经任务校准；本地 Core ML 版本仅移植推理，没有获得网球专项能力。因此，**不把 Laya 接入自动战术建议的决策链**。实验仓库、冻结基准和原始输出保留作可审计证据，不移植实验 UI 或模型权重到 RallyPath。

## 用户路径与第一版范围

1. 球员画出或打开自己的一分，选定要讨论的一拍；系统从现有画板读取双方站位、来球方向与落点、已有球路和拍次，不修改原画板。
2. 球员按需补充画板无法可靠推断的条件：接球者、正／反手、击球高度、来球快慢与旋转、是否赶得及／是否失衡、这次是想稳定回合还是练一项变化。未知可保留为未知；不把画板主题 Hard／Clay／Grass 当作真实场地物理信息。
3. 系统先检查**可执行性**：到位及击球窗口、该球员在类似条件下对目标球的掌握、落点容错和击球后的回位风险。第一版只使用教练审核过的、版本化的明确规则，缺关键条件或超出规则覆盖时弃答。
4. 只在未被排除的候选里比较战术目的：争取回位、保持相持、打开空档或结束回合。呈现最多两个可讨论选项，说明依据、主要风险和「这次先观察什么」；可跳回已有战术/练习画板。没有经过校准的数据时，显示条件和理由，不显示百分比或「最佳」标签。
5. 球员可以保留自己的选择、标记建议不适用，或练后记录「打得出／偶尔打得出／还打不出」及一个观察。记录是学习反馈，不自动当成模型真值。

首版只覆盖少量经教练确认的代表局面；不做原始视频识别、实时场边指挥、点胜率预测、儿童能力排名或自动诊断伤病。不能把现有演示规则直接搬入产品而跳过内容审查。

## 工程边界

| 层 | 首版做法 | 后续扩展条件 |
| --- | --- | --- |
| 局面提取 | 从 `src/board/model.ts` 的快照派生显式、带版本的局面字段；原画板仍是唯一内容主体 | 通过实际画板核对镜像、接球者、拍次与缺值；不依靠模板标题猜状态 |
| 可执行性 | 独立、可测试的规则模块输出 `可讨论／当前排除／信息不足` 和原因；球员自报能力与教练审查分开存 | 有同一球员、同类来球及不同目标的练习记录后，才训练个人执行模型 |
| 战术价值 | 引用现有战术内容及经教练审核的适用条件、目的和风险；不伪装概率 | 有实际击球、失误、对手回应和回位数据后，才估计候选的条件结果 |
| 建议输出 | 返回候选、排除原因、未知条件、规则版本和来源；接近或冲突时允许弃答 | 在独立新案例上验证后，才考虑数据模型排序与校准概率 |
| 文字辅助 | 自由文字可以辅助填字段和写解释，但结构化字段需让用户确认 | LLM／Laya 不直接决定球路，也不把解释生成当证据 |

实现时优先在现有应用内建独立的 `tactic-advice` 领域模块，与画板渲染、播放分离。建议和反馈采用独立、版本化存储，引用画板稳定 ID 与拍次快照；不往 `tennis-tactics:board-drafts:v1` 添加旧版会丢失的未知字段。保存、重开、复制、删除来源、JSON 备份／导入和旧版回退都需明确语义。没有有效画板编辑，不因查看建议而新建个人记录。个人能力与练习结果默认留在本机；如未来申请收集真实球员数据，另行确定监护人与球员同意、去识别和删除方式。

## 数据模型升级的门槛

先冻结新案例的评测集，让有经验的教练分别标记「可执行／危险／信息不足」及可接受的多个选项，保留分歧。同步收集球员在相近条件下真实练习的目标、落点、失误和回位。只记录实际选择的球不足以证明未选择的球更好；需要教练对候选进行评价，或在合适的练习设计中观察多种选择。

有足够覆盖且质量可核对的结构化数据时，可比较透明规则与表格模型（例如 CatBoost）的**执行结果**，再评估战术价值模型；不先上强化学习或比赛模拟。模型要按球员、训练场次和时间做隔离测试，避免同一回合或近似改写泄漏到验收集。上线门槛在看新测试结果前约定，至少检查危险建议率、可用覆盖率、教练可接受集合命中率、弃答是否合理、换一种等价表述／轻微位置变化的稳定性，以及真实球员是否看懂理由。未过门槛时继续人工讨论模式。

## 第一版验收例子

- 被快速来球拉出边线且低点击球时，不因为文字分数高就推荐高风险攻击；若球员能力未知，明确显示待核实条件。
- 球员在场内面对慢短球、对手后撤，但自报放短不稳定时，系统不能只按空档推荐放短；要给出更可执行的候选或弃答。
- 同一画板换接球者、改击球高度或改球员能力后，旧建议立即失效；回到原画板时原球路不变。
- 缺来球信息、无人能到位或所有候选都不适用时，显示「暂不建议」，不凑出一个最高项。
- 建议反馈保存失败不能显示成功；导出再导入后画板、建议版本和人工反馈仍能对应，旧版不会清掉新增数据。
- 青少年能在画板上看懂「为什么可以试／为什么暂时不适合」，并能选择自己的打法；工程测试和教练审核都不能代替真实用户试用。

## 与迭代计划的关系

这是 **v0.3 核心路径之后的独立候选功能**。先完成孩子自画一分并找到现有解法／练法的路径，再以最小场景验证「可执行性优先的建议」是否真的帮助理解；不把此方案写入 v0.2 已发布规格或承诺版本日期。启动开发前应从最新 `origin/main` 开短期功能分支，先完成场景卡、教练审核的候选与规则、数据保存方案和验收集，再做 UI。发布需另走 RallyPath 的既有 PR、回归和产品批准流程。
